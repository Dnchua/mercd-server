## 2. 客户端入口与消费方式【客户端源码】

### 2.1 StageSelect 五个页签

`StageSelectListParts.cs` 定义了 5 个页签，每个页签读取一个缓存键，并由一个 `consts` 开关控制能否点击：

| 页签 | 缓存键 | 数据来源 | 开关 | 本地当前值 | 原服录播值 |
|---|---|---|---|---|---|
| Story（主线） | `stages` | `/stages/` | 无 | — | — |
| HardMode（里世界） | `hard_mode_stages` | `/stages/` | `hard_mode_released` | `false` | `true` |
| Extra（特别） | `extra_stages` | `/stages/` | `extra_released` | `true` | `true` |
| Trials（试炼） | `specials` | `/team_quest/get_team_areas` | `trials_mode_released` | `false` | `true` |
| PastEvent（历史活动） | `events` | `/events/` | `event_mode_released` | `false` | `true` |

要点：
- 「试炼」页签读的是 `specials`（协力区域），而**不是** `/trials/`。日替试炼只是这个列表里 `type="trials"` 的一个入口。
- 本地 `serve_preset_data.json` 里 `event_mode_released=false`，所以即使 `/events/` 返回数据，玩家点击页签也只会弹出「功能即将开放」。M8 必须由服务端下发改为 `true`。

### 2.2 历史活动列表的点击逻辑

`EventListRow.cs` 和 `EventStageListRow.cs`：
1. 先计算 `release_limit − 服务器时间`。
2. 如果大于 0，打开 `ReleasedEventAreaSelect` 页面，页面参数直接取该行的 `release_event_select_option`。
3. 如果小于等于 0，弹出确认框，花徽章调用 `/events/release?id=<id>` 解锁（提示文案中会显示当前徽章数）；返回 `status=success` 后再打开页面。
4. 新手教程账号一律弹出教程锁。

录播中 42 条活动的 `release_limit` 全部是 `1823324399`（2027-10-12 14:59:59 +08），也就是**全部处于已解锁状态**。`/events/release` 的请求与响应格式在录播中没有出现【缺口】。

### 2.3 区域与关卡筛选

`ListFilterComponent.BeforeLoadListRows` 的规则：列表行的 `id` 如果大于边界值 `cache[border.data][border.key]`，就把这一行移除。所以：
- `user_event_condition_<event_id>.area_id` 决定能看到哪些区域，`.quest_id` 决定能看到哪些关卡。这两个值就是账号在该活动中的**推进边界**。
- 区域完成率：区域行带 `percentage` 字段时直接显示该值；否则客户端按「`normal_clear > 0` 的关卡数 / 关卡总数」自己计算（`AreaSelectParts.cs:109-121`）。

### 2.4 周常页（DailyQuestSelect）

`DailyQuestSelectParts.cs`：
- 缓存键是 `daily_quests_<星期>`，星期取客户端 `Common.Now.DayOfWeek`（周日=0 … 周六=6）。如果缓存里没有这个键，会强制请求 `/quests/daily` 并从响应中读取同名键。
- **列表必须至少 4 行**，并按顺序映射到初级、中级、高级、特级四个按钮。按钮显示 `use_ap` 和 `clear_count`。
- 开战消息为 `name=Quest&base=Quest/Quest&mode=quest&id=<行 id>`，所以每一档都是一个**独立的关卡 id**，不使用同一关卡的四个难度。
- 入口有两个：主线区域选择页的 `DailyQuestBanner` 部件（贴图 `common/daily-<星期>`），以及首页活动轮播 `banner_daily_quest`（「一周探险」）。

由此可见，服务端下发的星期和客户端本地星期必须一致。如果跨日时两边对不上，客户端会因为找不到缓存键而重新请求【推断】。

### 2.5 试炼入口（TrialsStageListRow）

`type` 分三种：
- `team_quest`：进入 `TeamQuestAreaSelect`，请求 `/team_quest/get_team_quests?area_id=`。
- `team_quest_shop`：进入协力商店。
- `trials`：进入 `TrialsQuestSelect`，请求 `/trials/daily?wday=<wday>`。

### 3.3 观察

1. **两个 id 系列**：1–40 一个系列，区域键是 `areas_10NN`，与 `stage_id = 1000 + event_id` 对应（当期活动 44 的 `stage_id` 是 1044，可作旁证）。另一个是 100000+ 系列，**区域键与 event_id 不一一对应**，例如 100004 → `areas_100002`、100017 → `areas_100018`，只能逐条按表下发，不能用公式推导。
2. **id 不连续**：缺 4、9、12、18、22、24、28、32、35、41、42、43。其中 41 在本地 app_conf 里有独立页面 `EventAreaSelect`（requireData 为 `/areas/event?event_id=41`），43、44 没有出现在历史列表里（44 是当期活动）。
3. **区域 id 规律【推断】**：当期活动 44 的区域 id 是 4176–4178，正好等于 `4000 + 4×44` 起算的连续 3 个；本地 `inputs/files/area/` 中的 `area_40xx`/`area_41xx` 资源也完全落在 `4000+4N … 4000+4N+3` 区间内（见上表最右列）。所以 1–40 系列每个活动最多 4 个区域，区域 id 为 `4000+4N+k`。100000+ 系列的区域图在 `area_100000 … area_100042` 中有 30 个，与 event_id 的对应关系没有足够证据。
4. **按国服时间线排列**：列表下发顺序是两个系列交错的，看起来是按国服实际开放时间排序【推断】。

### 3.4 缺口
- 41 个历史活动的 `/areas/event?event_id=N` 全部没有录播，包括区域名、关卡、AP、波次、掉落和完成率奖励。
- `/events/release` 的扣费额度与响应格式。
- `event/event_<id>` 横幅贴图（`EventStageListRow` 用，`EventListRow` 只用文字）在 `inputs/files` 中没有对应目录。
