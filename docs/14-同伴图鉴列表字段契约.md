# 同伴图鉴列表字段契约与裁剪

2026-11-04，本次仅修改 mercd-server 的 Go 返回映射，不构建 APK、不进入实机。接口实际路径为 `/albums/`；`/ablumns` 是任务描述中的拼写。

## 问题与证据

原实现将 `buildUnitDoc` 的完整同伴文档直接作为每条图鉴记录，叠加图鉴状态后返回。该文档包含战斗行为、抗性、技能、成长预览、简介档案等详情字段；图鉴全目录中的每行都重复携带，增加传输、解密解压、JSON 解析和缓存对象的负担。

客户端消费根据既有 CN3.5 客户端反编译源码核对，未修改或重新解码 DLL：

| 消费点 | 所需内容 |
|---|---|
| `UserAlbum` 的 app_conf `filter` / `SortOption` | 性别、稀有度、属性、武器、国家及排序数值 |
| `AlbumSelectParts.LoadListRowsCore` | 全目录在客户端筛选排序，每页 12 行，不能只返回持有子集 |
| `AlbumButtonsListComponent.GetHeaderLeftLabelText` | 分子为非 hide 行，分母为目录总行数 |
| `AlbumButtonsListComponent` | 模式字符串、详情入口及警告标记 |
| `AlbumListRow.UpdateBatchSprite` | id、protected、is_waiting |
| `UnitListRow` 的图鉴显示模式 | 名称、星级、持有/待机等级与觉醒次数、进化状态 |
| `GalleryParts` / `GalleryListRow` | 名称与 id；图片路径由客户端根据 id 生成 |
| `AlbumUnitDetail.OnPrepare` / `LoadDocuments` | 持有单位从 `user_units` 查找；未持有单位按 `data_path` 请求 `album_unit` |
| `AlbumUnitDetail.UpdateDisplay` | 从 albums 补读警告、觉醒上限和待机信息；面板与档案来自详情文档 |

原作观测：只读检查 MLK 解密材料中 13 份 `/albums/` 响应，每份 1,326 行，字段并集 34 项，类型与下表一致；原始材料和客户端源码不纳入本次公开变更。这证明原服列表与详情有独立契约，不证明本地客户端卡死的唯一原因。

## 当前下发字段

`buildAlbumRow` 使用显式白名单，从既有同伴映射中保留列表字段，再加入图鉴态。最多 32 项，模板缺失的可选值不补造。详情文档仍使用原映射。

| 用途 | 字段 | JSON 类型 |
|---|---|---|
| 标识与名称 | `id`, `order_num` | number |
| 名称 | `name`, `main_name`, `prefix_name`, `rare_type_name` | string |
| 筛选 | `rare_type_id`, `attr_id`, `weapon_id`, `country_id`, `sex_id` | number |
| 排序 | `at_max`, `hp_max`, `speed`, `reach`, `taghness`, `age` | number |
| 显示与保护 | `hide`, `protected`, `is_leader_unit` | boolean；protected 仅持有时下发 |
| 模式过滤 | `is_user_unit`, `is_waiting`, `is_showable` | string：`"true"` / `"false"` |
| 持有态与上限 | `user_unit_level`, `user_unit_duplicated_count`, `max_duplicated_count` | number |
| 警告 | `unit_alert`, `wait_alert` | boolean |
| 进化 | `is_evolutable`, `can_evolution_level`, `evolution_map` | boolean / number / object |
| 详情入口 | `album_detail_message` | string：保留 PageMessage 与已转义的 data_path |

MLK 另外观测到 `waiting_unit_level`、`waiting_unit_duplicated_count` 两个 number 字段；当前库存尚无待机状态，沿用省略策略，客户端显示缺省 `-`。无待机、进化未开放和警告默认值等既有重建策略，本次未扩展其业务能力。

列表移除 `hp`、`at`、`level`、`max_level`、成长区间、技能、战斗行为/抗性、素材路径及长篇档案等详情数据。`data` 顶层仍有 `albums`、`album_data`、`user_bg_options` 和 `country` / `sex` / `weapon` 枚举，保障现有详情与画廊读取。

## 本地验证

定向测试覆盖加密 game 通道、完整目录、持有/未持有形态、双账号隔离、空库存、重复读取、详情路径、非法详情参数和读取零库存写入。新增检查从实际 app_conf 提取筛选/排序键，并限制列表字段与平均每行 1,100 字节预算，防止完整同伴文档再次混入。

在 `server/` 执行定向测试 `go test ./internal/cn35game -run 'TestAlbum|TestMonsterAlbum|TestInventoryListChain' -count=1 -v` 以及全量 `go test ./...`，均通过。

相同现有会话、只读 SQLite、进程内处理器，使用 `go run ./cmd/cn35perf -n 3` 在修改前后各测一次（一次预热另计）。报告只含指标，不保存凭据与响应原文：

|---|---:|---:|

| 解密后 JSON 字节 | 6,166,198 | 1,406,385 |
| 加密响应字节 | 774,096 | 125,792 |

本次裁剪发生在同源文档构建之后，尚未消除完整文档构建和逐模板查询成本；没有修改查询、数据库或共享同伴映射。

## 同伴列表实机续测

2026-11-04 使用 Android 12 Redroid、分离版 APK 和同一测试账号的 1,251 名持有同伴复测。用 ADB 在点击前写时间标记，以 Unity `Page Load Done : UserUnits` 为开页终点（源码在启用触摸后写此日志）。服务端请求记录与设备日志交叉核对。

| 列表条件 | 点击至页面就绪 | 期间 `/albums/`、`/user_units/`、`/user_monsters/` 请求 |
|---|---:|---:|
| 全部 1,251 条，第 1 次计时 | 41.179 秒 | 0 |
| 全部 1,251 条，第 2 次计时 | 36.187 秒 | 0 |
| 同一库存，界面筛选为 80 条 | 1.290 秒 | 0 |

首次访问（没有点击标记）中，`/albums/` 服务端处理 175 ms、设备侧请求 394 ms，收包至页面就绪仍有 35.529 秒，期间出现一次 `unit_list_169` 的 APK 内资源加载超时。后续两次全量列表均未再出现这条超时；第 2 次开页期间采样到 `UnityMain` 平均占用一个 CPU 核心的 99.9%。筛选实验仅改变客户端展示数量，未修改库存或服务端返回。

实机证据表明，字段裁剪后全量同伴列表仍有约 36–41 秒的等待，主要瓶颈在客户端处理大量列表行。`UnitListParts.LoadListRows` 经过排序后，`ListParts.LoadListRowsCore` 为每条匹配记录创建完整行或占位行，`AfterGridReposition` 再把行加入逐帧检查列表。该静态链路解释了行数对性能的影响；没有方法级采样结果，尚未量化排序、行构建和逐帧检查各自的耗时。

## 国家字段与原服对照

2026-11-04 只读检查 MLK 解密响应：`/user_units/` 样本的持有数量为 148–242，`/albums/` 为 1,326；其中一份 241 人样本的 `user_units` 数组约 699,891 字节。原服样本不是本地测试账号，不能直接比较开页耗时。

同日核对本地测试账号及运行中服务的实际响应：1,251 条 `user_units` 和 1,829 条 `albums` 的 `country_id` 全为 0。原因是数据库名册覆盖层由 `UnitFromTemplate` 重建单位时未恢复 `CountryID`；静态目录原有的按最小单位 ID 编号也不能保证匹配客户端国家筛选配置。

修复前在同一账号、设备、库存和“全部”筛选条件下，从菜单点击到 `Page Load Done : UserUnits`，按排序分别测量两次；各轮期间列表 API 请求均为 0：

| 排序 | 第一次 | 第二次 |
|---|---:|---:|
| 编队同伴 | 37.949 秒 | 39.891 秒 |
| 等级降序（等级全为 1） | 38.103 秒 | 40.138 秒 |
| 稀有度降序 | 35.693 秒 | 36.219 秒 |

样本量很小，不能量化排序耗时；结果不支持把几十秒等待主要归因于等级同值。测试仍无法直接区分占位对象创建、对象池查找、布局与逐帧检查的占比。

修复后，已知国家使用 CN3.5 配置中的筛选 ID；少数名称别名由目录与原服观察交叉核对。未知国家分配从 200000 开始的确定性重建 ID，不宣称原服值，也不能保证命中客户端“其他”筛选；覆盖层出现静态目录中不存在的未知国家时不伪造 ID。相同 ID 的枚举行去重。用当前源码及该账号只读处理器验证，`user_units` 产生多个国家 ID，例如王国 189 条、沙漠 42 条。缺失或重建国家仍可能影响国家筛选和同国 SP 加成，不能据此声称所有国家数据已验收。

验证版替换运行进程前，以 SQLite backup 生成一致性备份并保留原二进制，`quick_check` 为 `ok`。修复版服务的实际响应也确认王国 189 条、沙漠 42 条。重新进入 `test001` 后，客户端筛选弹窗显示王国 189、妖精 55、机械 65；选择王国显示 189/1,251，应用后列表显示“王国”。修复后一次全量首次开页为 38.112 秒（含缓存加载，不能与上表无请求的重复开页严格对比），未验证同国 SP 加成的实际战斗表现。`go test ./...` 通过，另有定向测试检查配置中的国家筛选 ID、模板覆盖和两个接口的响应。
